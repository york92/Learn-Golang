# 架构与设计思路

## 1. 总览

```
 Web 浏览器            App / imcli
     │ WebSocket(/ws)      │ TCP :9000
     │ 同一套二进制帧       │
 ┌───▼─────────────────────▼──────────────────────────┐
 │ gateway   连接层：握手认证 · 心跳/空闲检测 · 限流     │
 │           每连接 读/写 两个协程 · 可靠推送(ACK+重传)  │
 └───┬─────────────────────────────────────────────────┘
     │ Backend 接口（HandleSend / HandleSync / HandleRead / Authenticate）
 ┌───▼─────────────────────────────────────────────────┐   ┌──────────────┐
 │ service   业务层：校验 → 落库 → 推送；好友/群/会话     │◄──┤ api  HTTP 层  │
 └───┬─────────────────────────────────────────────────┘   │ 注册登录/好友 │
     │ 方法调用                                             │ 历史/会话/Web │
 ┌───▼─────────────────────────────────────────────────┐   └──────────────┘
 │ store     内存索引 + WAL 追加日志（data/wal.jsonl）    │
 └─────────────────────────────────────────────────────┘
```

**为什么这么分层：**
- `gateway` 完全不懂业务，只认 `Backend` 接口。因此换成「网关 + 独立逻辑服务（gRPC）」只需要实现这个接口的远程版本。
- `service` 不关心连接，只通过 `Pusher` 接口"把这段字节推给某用户"。
- `store` 是唯一持有状态的地方，将来换 MySQL/Redis 只动这一层。

## 2. 一条消息的完整旅程

```
A 客户端        网关              service              store            网关          B 客户端
  │ SendReq ────►│ 限流/解析        │                    │                │              │
  │ (client_msg_id)│──HandleSend──►│ 校验(内容/好友/群)    │                │              │
  │               │                │──AppendMessage────►│ ① 幂等检查       │              │
  │               │                │                    │ ② 分配 msg_id/seq│              │
  │               │                │                    │ ③ 写 WAL ← 落盘点 │              │
  │               │                │                    │ ④ 写各收件箱     │              │
  │◄── SendAck ───│◄───────────────│◄─ {msg_id,seq} ────│                │              │
  │ (✓ 已发送)     │                │ fanout：每个收件人各自 user_seq        │              │
  │               │                │────────────PushToUser(B)─────────────►│── Push ────►│
  │◄── Push(回显) ─│ (A 的所有设备也会收到，含发送设备)                        │◄─ PushAck ──│
```

**关键顺序：先落库，再 ACK，再推送。** 如果反过来，"推送成功但落库失败"会让消息凭空出现又消失。
推送失败、对方不在线都不影响正确性——消息已在收件箱里，对方上线后 `sync` 补齐。

## 3. 可靠性模型：至少一次 + 幂等 = 效果上恰好一次

| 要保证 | 机制 | 位置 |
|---|---|---|
| 不丢（上行） | 客户端等 `SendAck`，超时用**同一个** `client_msg_id` 重发 | client / web |
| 不丢（下行） | 推送要求 `PushAck`，未收到则按间隔重传（默认 3s×3 次）；仍失败则靠 `sync` | `gateway/conn.go` |
| 不重 | 服务端按 `(发送者uid, client_msg_id)` 去重（落库时判断，重启后由 WAL 重建）；客户端按 `msg_id` 与 `user_seq` 游标去重 | `store.AppendMessage` / client |
| 不乱序 | 会话内 `seq` 单调递增连续；UI 按 `seq` 排序，**不信任客户端时钟** | `store` |
| 不漏 | 收件箱 `user_seq` 连续；客户端发现空洞（来了 5 但游标在 3）就 `sync(since=3)` | client / web |

**两个序号各管一件事：**
- `seq`（会话内）：决定消息在某个会话里的**显示顺序**，也是**未读数**（`最新seq − 已读seq`）与**已读位置**的度量。
- `user_seq`（用户收件箱）：决定"我这个用户**错过了什么**"，是**同步游标**。单聊和群聊的消息都进同一条时间线，所以一个游标就能补全所有会话。

## 4. 收件箱时间线（Timeline）与"快照 + 增量"

```
inbox[bob] = [ m(alice,#1) , m(alice,#2) , m(群team,#1) , ... ]     下标+1 = user_seq
bob 的手机游标 = 2    →  上线后 sync(since=2)  →  拿到 user_seq=3,4,...
```

- 多设备天然成立：每台设备各自维护游标，服务端只有一份收件箱。
- 新登录/刷新页面：先 `GET /api/conversations`（拿**快照**，同一把读锁里返回 `latest_user_seq`），再从这个游标起 `sync`（**增量**）。快照与游标一致，所以不会漏也不会重。
- 推送只是"加速"：真正的数据通道是 `sync`。这也是为什么重传次数用完后可以直接放弃。

## 5. 群聊：写扩散

发一条群消息 = 消息体只存 1 份（`convMsgs`），再往**每个成员**的收件箱各写一条引用（只有指针，几乎不占空间）。
读取与同步因此极简（和单聊同一条路径）。代价是大群写放大（500 人群 = 500 次收件箱写入）。
当前上限 500 人/群；万人大群需要改成读扩散，见 ROADMAP。

## 6. 存储：WAL + 内存索引

**写路径（所有写操作同一个模式）：** 校验 → 构造 record → 追加写 `wal.jsonl` → `apply` 到内存。
**启动：** 顺序回放 WAL，用同一个 `apply` 重建全部状态，所以内存与磁盘不可能不一致。

| 设计点 | 做法 |
|---|---|
| 崩溃安全 | 记录以 `\n` 结尾；回放时遇到不完整的尾行就截断丢弃（`TestReplayAndTornTail`） |
| 持久性 | 后台每 `fsync_ms` 毫秒 fsync 一次（组提交）；设 0 则每次写都 fsync |
| 幂等表 | 不单独存，回放消息记录时顺便重建 |
| ID 接续 | `nextUID / nextGID / nextMsgID` 在回放中取最大值+1 |
| 密码 | PBKDF2-HMAC-SHA256，6 万次迭代，16 字节随机盐，常数时间比较；用户不存在时也做哈希，避免通过耗时探测用户名 |
| 令牌 | 32 字节随机数，带过期时间，可吊销；也写 WAL（重启后仍有效） |

**取舍：** 全量驻留内存 + 无压缩，换来零依赖和极简的代码。文件会一直增长（只追加），适用于中小规模；
需要更大规模时换存储，`service` 层只依赖 `store` 的方法集（见 ROADMAP）。

## 7. 连接层要点（gateway）

- **每连接两个协程**：`readLoop` 读帧分发；`writeLoop` 从有界队列取数据，用 `writev` 批量写出。读写分离使慢写不阻塞心跳读取。
- **Send 永不阻塞**：队列满（慢消费者）就断开该连接，保护内存与其他用户；客户端重连后靠 `sync` 追平。
- **空闲/假死检测**：每读到一帧就重设读超时（心跳间隔 × 3 的量级）。TCP keepalive 抓不到 NAT 老化、对端断电等"假死"，必须靠应用层心跳。
- **认证超时**：建连后 10 秒内必须完成认证，防"占坑"。
- **帧长度先校验再分配内存**：防 OOM 攻击（TCP 与 WebSocket 都如此）。
- **同设备重复登录踢旧留新**；`Manager.Remove` 只删"自己"，避免快速重连时误删新连接。
- **优雅停机**：停止接入 → 给每个连接下发 `Kick{retry_after_ms: 随机}` → 排空 → 超时强制关闭。随机化让客户端错峰重连，避免"惊群"。
- **WebSocket 复用**：握手后把 WS 包装成 `net.Conn`（读=拼接消息负载，写=一帧一个 binary 消息），上层 `Conn` 逻辑零改动。

## 8. 客户端要点（Web / Go SDK 共用同一套思路）

1. 认证成功后立即 `sync(since=游标)`，补离线期间的消息。
2. 收到推送：**先 ACK 再处理**（无论重复与否都要 ACK）；`user_seq <= 游标` 丢弃；`== 游标+1` 推进游标；`> 游标+1` 暂存并触发 `sync` 补洞。
3. 发送：本地回显 → 等 `SendAck` → 超时用同一 `client_msg_id` 重试（最多 3 次）→ 仍失败标红，点击重试。
4. 心跳 + 假死检测（2.5 个心跳周期没收到任何数据就主动重连）；重连用**指数退避 + 抖动**，被 Kick 时遵循 `retry_after_ms`。
5. 未读数 = 本地 `lastSeq − read_seq` 推导，而不是累加计数——这样重复收到、多端已读都不会算错。
